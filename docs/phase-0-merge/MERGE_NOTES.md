# Merge notes

The original bundle had two separate projects: `AdRIC_DB` (Express + Prisma + MariaDB
backend) and `AdRIC_FE` (Vite + React frontend). They were combined into one project
rooted at `AdRIC_System/`. Unique files were carried over as-is. Conflicting files
(same purpose, different content) were resolved as described below.

## How the two halves actually connect

- `server.ts` runs the API on `http://localhost:4000` and imports the Prisma client
  from `./generated/prisma`, which is generated from `prisma/schema.prisma`.
- Most frontend components already call the backend directly, e.g.
  `fetch("http://localhost:4000/api/...")` (ITSDashboard, CustodianPortal,
  LabHeadDashboard, Loan/Return/Repair/Transfer forms).
- A few frontend files (`Login.tsx`, `context.tsx`, `NotificationCenter.tsx`) still use
  `src/app/prismaClient.ts`, which is a localStorage mock that imitates the Prisma API.
  It was left untouched so nothing that currently works breaks.

## Conflicting files and how each was resolved

### `prisma/schema.prisma` (the main conflict)
The two schemas describe the **same** MariaDB database in two different ways:

- `AdRIC_DB/prisma/schema.prisma` — newer, snake_case models (`users`, `assets`,
  `asset_records`, `asset_loans`, `asset_returns`, `asset_transfers`, `projects`, ...),
  `provider = "prisma-client"`, `output = "../generated/prisma"`. This is what the
  generated client and `server.ts` actually depend on.
- `AdRIC_FE/prisma/schema.prisma` — older, PascalCase models with `@@map` (`User`,
  `Asset`, `AssetRecord`, `CustodianshipTransfer`, ...), `provider = "prisma-client-js"`.
  This was a design-time schema; nothing at runtime depends on a client generated from it.

These cannot be blindly unioned: both target the same tables, so keeping both would give
Prisma two models mapping to one table (e.g. `users` and `User`) and fail generation.
**Resolution:** the backend schema was kept as the single authoritative
`prisma/schema.prisma`. The old FE schema was preserved for reference at
`docs/reference/schema.fe-design.reference.prisma` (nothing imports it).

### `package.json`
Merged into one root file:
- Dependencies = frontend deps + backend runtime deps (`express`, `cors`, `dotenv`,
  `@prisma/client`, `@prisma/adapter-mariadb`).
- `react` / `react-dom` (18.3.1) were moved from `peerDependencies` into `dependencies`
  so a fresh `npm install` reliably pulls them for this standalone project.
- devDependencies = frontend devDeps + backend devDeps (`prisma`, `tsx`, `typescript`,
  `@types/*`), plus `concurrently` for the `dev:all` script.
- `"type": "module"` is used (Vite requires it; the backend is ESM-safe — it uses
  `import.meta.url`, no `require`/`module.exports`).
- Scripts: `dev` (frontend), `server` (backend), `dev:all` (both), `build`, `seed`,
  `prisma:generate`, `prisma:pull`.

### `package-lock.json`
Both originals were dropped. They locked two different dependency sets and cannot be
hand-merged. A single fresh lockfile is produced by running `npm install` on the merged
`package.json`.

### `.gitignore`
Only the backend had one. It was extended with the frontend's build output (`dist`) and
tooling caches (`.vite`).

### `README.md`
Replaced with a combined README covering setup and running both halves.

## Not included

- `node_modules/`, `dist/`, and Prisma engine caches from both originals were left out;
  they are regenerated by `npm install` / `npm run build` / `npm run prisma:generate`.
- `generated/prisma/` (the backend's generated client) **was** kept, because `server.ts`
  imports it directly; regenerate it with `npm run prisma:generate` if your schema changes.

## Known quirks worth cleaning up later (not changed here)

- The frontend is mid-migration: some files hit the live API, others still use the
  localStorage mock (`prismaClient.ts`). Over time those mock-backed screens can be moved
  to real `fetch` calls too.
- `@types/react` is v19 while the React runtime is 18.3.1. This mismatch existed in the
  original frontend and is compile-time only (Vite/esbuild does not type-check on build).

## Update: full file inclusion

Every non-`node_modules` file from both halves is now included:

- `ATTRIBUTIONS.md` — carried over from the frontend.
- `dist/` — the frontend's prebuilt output (static bundle). Regenerated by `npm run build`.
- `docs/reference/` — the ORIGINAL files that were merged or replaced, kept verbatim so
  nothing is lost:
  - `package.DB-original.json`, `package.FE-original.json` (the two originals behind the

  - `package-lock.DB-original.json`, `package-lock.FE-original.json` (the two original
    lockfiles; the merged project regenerates a single lockfile on `npm install`)
  - `README.FE-original.md`

### Why `node_modules/` is not merged
The two `node_modules/` folders cannot be correctly combined by copying. They contain
overlapping dependencies at different versions (both include Prisma, TypeScript, etc.),
so unioning them produces version conflicts. They also hold OS-specific compiled binaries
(Windows `esbuild.exe`, the Windows Prisma query engine, native `.node` files) that only
run on the machine they were built for. The single correct `node_modules` for the combined
project is produced by `npm install`, which resolves everything from the merged
`package.json`. That is why installation is a required step, not an optional convenience.
